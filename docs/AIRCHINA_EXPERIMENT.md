# 国航实验任务架构与携程对照

更新日期：2026-10-30。此功能不是正式报价/甩尾适配已验收。

## 六层链路

```text
网页「国航实验」 / JSON API
  → ExperimentalQueryService（后台任务、公共 run_lock、人工继续、取消）
      → ExperimentalSessionRunner（专用线程/长驻事件循环，浏览器对象不跨循环）
      → ExperimentalBrowserSession（可选短时同页复用，有限寿命）
  → QueryService.inspect_airchina_experiment（总时限、浏览器生命周期）
  → BrowserAutomation / BrowserSessionManager / ProviderRuntime（公共设施）
  → providers/airchina.py（一次导航及查询编排）
      → airchina_form.py / airchina_form.js（可选首页表单，一次提交，不回退直达）
      → airchina_page.py（入口校验、验证码/限制/过期/提示状态）
      → airchina_result_wait.py（有界等待，两次经校验的票价证据一致）
      → airchina_parser.py / airchina_products.py（航班/舱位/产品绑定）
      → airchina_result.py（参考结果组装，不生成正式 price）
  → PriceRepository.experimental_query_jobs（独立任务/参考结果记录）
```

没有另复制一套浏览器引擎、SQLite 连接或公共查询锁。实验查询与普通查询、
甩尾任务互斥；不读取任何平台的加密凭据或 Fliggy key。
参考结果不写入 `price_snapshots` / 甩尾结果，不参与报表、比价、路线学习和负缓存。
加载/过期/人工提示不可作为有效列表；若产品读取阶段失败，丢弃此前列表预览，
不让早先读到的价格继续冒充本次有效结果。

## 用法与生命周期

网页入口为顶部的「国航实验」。配置需包含 `airchina` 项，但保持
`enabled=false`，不需要启用普通监控。仅接受明确机场、未来单程日期、
1 成人、经济/公务舱；可选指定航班产品，否则只读列表。
总时限 240 秒，包含浏览器启动、人工等待与读取；取消/超时后关闭上下文。
网页新任务默认 `session_mode=reuse`；API 省略仍为 `fresh`（每任务关闭），
二者都使用原有持久档案机制，不把“重启对照”理解为清空 Cookie 的全新身份。
网页默认勾选“自动确认查询通知，并记录内容”；可取消勾选。
API 必须显式传入 `auto_confirm_notices: true`，省略默认保持人工模式；
历史任务不因升级自动获得此授权。CLI 保持人工模式。
已授权的查询通知先持久化正文再确认；不处理验证码、登录授权、个人声明、
预订/支付、过期刷新或未知弹窗。网页新任务默认 `interaction_mode=stop`：
出现验证或未知提示后结束任务、关闭上下文并释放锁，不自动重试，不判为无票。
显式选择 `interaction_mode=wait` 时，需要人工的结果页场景停在 `waiting_user`，用户在
**项目浏览器**处理后点击继续，读取同一个页面，不重新搜索。
最多接受 3 次人工继续。
API 省略 `interaction_mode` 保持旧的 `wait` 语义；新网页明确提交 `stop`，
不会改变历史任务模式。表单提交前遇阻仍直接结束，不提供重新提交式“继续”。
应用关闭会请求取消；重新启动会把遗留活动任务标为 `interrupted`，
不会假装恢复旧浏览器会话，也不会自动重新提交。
部署范围是现有单进程本地应用；不提供跨进程分布式互斥。

API：

- `POST /api/experiments/airchina`：白名单字段
  `origin / destination / departure_date / cabin / flight_no / auto_confirm_notices / entry_mode / interaction_mode / session_mode`，
  返回 202 和任务 ID；自动确认参数只接受 JSON 布尔值。
- `interaction_mode` 仅接受 `stop` / `wait`；不是自动解验证码授权。
- `session_mode` 仅接受 `fresh` / `reuse`。
- `GET /api/experiments/airchina`：最近任务；
  `GET /api/experiments/airchina/{id}`：详情。
- `POST /api/experiments/airchina/{id}/continue`：当前任务等待人工处理时有效。
- `POST /api/experiments/airchina/{id}/cancel`：取消当前任务。
- `POST /api/experiments/airchina/session/close`：关闭空闲浏览器，不清除持久档案；
  有任意查询运行时拒绝，不取消别人的任务，也不重发搜索。
- 共用现有本地 Origin 校验及可选 UI token 校验；忙时 409。
- `completed_reference` 仅表示参考票价，不是完整报价成功；
  `inconclusive` 不是“无票”。断网不自动重复 POST，须刷新确认服务端状态。

CLI 诊断仍可用，输出仍在忽略的 `runtime/airchina_probes` 中；
网页任务不依赖这些文件，不记录整页文本、截图、网络响应或任意异常消息。

## 列表等待与诊断

列表阶段最多等待 `min(provider.timeout_ms, 30000)` 毫秒，默认每 500 毫秒
采样一次；仍受任务 240 秒总时限约束，不重新导航、不重发搜索。
每次独立校验 URL、可见航线/日期/人数、单程标识、票价口径和舱等列。
连续两次的标准化报价及列表质量证据相同才接受；产品展开、说明文字等
无关 DOM 变化不再让列表一直“不稳定”。价格变化、上下文失配、加载或
安全状态不明会重置稳定计数；验证、限制、过期及页面偏离仍立即停止。

页面新增“读取诊断”，展示采样次数、耗时、最后解析原因、可见行/拒绝行/
筛除/冲突数量、缺失的可见条件及页面状态。拒绝行原因按固定代码计数，
如机场不匹配、时长不符、报价格式未知；不记录行原文。
保留最多 8 次状态转换摘要，不保存原始 DOM、整页文本、完整 URL 或价格
到诊断字段。字段“存在”不等于“匹配”，是否匹配仍由严格解析器判定。
任务顶层 `diagnostics` 在状态变化时保存，取消、失败、总超时仍保留最近
采样；不是对结束时官网状态的保证。没有旧记录的诊断不会回填或伪造。

已观察到的“查询无结果～ 可尝试更换日期或稍后重试”记录为
`page_reports_no_results`。只证明当次可见页面显示此提示，不代表无票、
航线不存在或完整覆盖，不写负缓存，不取旁边日历价格当航班价。
提示若在等待期限内消失，仍可接受后续严格校验且稳定的航班列表。

## 查询通知自动确认与记录

`airchina_notices.js` 仅采集实际观察到的 `dialog_mainContent__` 内
`model_header__` / `model_body__` / `model_footer__`，不读取整页或 iframe 内容、
输入框、cookies、网络响应。`airchina_notices.py` 对原始正文及按钮校验，
记录时去除 URL 查询参数、片段、邮箱、长号码与明显密钥；前端用 `textContent`
展示文字，不执行 HTML、不自动打开其中链接。

仅确认同一官方航线查询页上的单个、结构明确的通知弹窗，按钮必须是
“确认，查看下一个提示”或“我知道了”。确认前重新检查页面和正文，
确认后检查弹窗关闭或内容更换；不会仅因 click 返回就宣称处理成功。
同一内容不重复点击，每任务最多记录/处理 10 条，防止弹窗循环。
存在验证码、访问限制、过期提示、表单输入、个人声明、支付/预订含义、
多弹窗或未知按钮时停止自动操作；不能可靠识别时仍需人工处理。
这不是通用“关闭所有弹窗”工具。

任务顶层 `notices` 独立保存：

- `title / body / button`：可见通知内容（敏感模式脱敏，超长内容截断且不自动确认）。
- `observed_at / processed_at`：采集及可见转换确认时间。
- `status`：已记录、准备点击、已点击待确认、已自动确认、需人工或结果未确认。
- `reason / notice_id / source`：处理依据、去重标识和来源。

记录写入失败不点击；超时/取消/任务失败/重启后保留已写入内容。
页面的“官网提示记录”在无报价时仍可展开，展开状态不会被轮询收起。
记录不代表已验证乘机资格，也不是对通知内容的独立法律/安全核验。

2026-10-30 实测：项目 Chrome 在 PEK→SHA、2026-11-10 查询页自动处理
3 条通知（充电宝安全、登机口通行、T3 楼间通行），均记录为
`auto_confirmed`，包括最后一条“我知道了”。随后票价解析仍为
`inconclusive`，没有写入正式价格快照；不得据此声称完整查价已通过。
公开通知样本位于 `tests/fixtures/airchina_travel_notices.json`（链接参数已去除）。

同日 21:25（Asia/Shanghai）使用新诊断再次查询 PEK→SHA、2026-11-10、
CA1549：3 条通知均自动确认。列表阶段 29.8 秒、60 次采样，最后原因为
`page_reports_no_results`，采样期间未记录到其他解析状态；可见行数 0，
加载/验证码/访问限制/过期/待确认通知信号均为 false，价格口径文本缺失。
任务仍为 `inconclusive`，正式快照为 0。这次证据定位到“官网可见空结果页”，
而非仅仅整页 DOM 不够稳定；不能推断真实库存不存在，也尚不能确定网站
空结果的上游原因。下一步应对照正常表单入口与直达结果页，不盲目增加重试。

## 表单入口与直达入口对照（2026-10-30）

在同一应用内浏览器中，保持 PEK→SHA、2026-11-10、单程、1 成人：

| 路径 | 实际观察 | 现有解析器回放 |
|---|---|---|
| 首页选择单程并点“查询”，用户人工完成安全验证 | 16 个可见航班行，显示每成人不含税口径，无剩余遮挡通知 | 16 个经济舱参考起价，拒绝行 0；CA1549 16:30–18:45，¥600 起 |
| 随后在同一应用内浏览器新标签直接打开完全相同结果 URL | 3 条通知确认后仍显示“查询无结果”，0 航班行；未显示验证码 | `page_reports_no_results`，无报价，不视为无库存 |

这组证据说明现有 DOM 解析器能处理本次真实成功列表，且仅有正确结果 URL
不足以保证查价成功。它支持继续调查入口/页面初始化流程，而非放宽价格
校验或把日历价格当结果。它**没有**隔离表单操作、人工验证、标签页内状态、
加载时序和站点响应等变量，不能断言缺少某个 Cookie、请求头或接口参数。
没有读取/导出 cookies、storage、网络响应或挑战凭据，也没有切换后端绕过验证。

此对照是在应用内浏览器完成，不是项目 Chrome 的自动表单查询验收。
对照时项目仅有直达模式，尚未新增自动表单入口或自动 fallback。
由此确定下一步增加**显式可选的表单实验入口**：真实选择机场、日期和人数，
提交前复核条件；人工验证后沿用同一页面；复用现有通知处理、解析和诊断。
不能仅复制 URL 或复用应用内验证状态，更不能因空结果无限重试。

公开 DOM 配对样本为 `tests/fixtures/airchina_entry_comparison.json`；
仅包含查询上下文、航班/舱等公开字段和布尔状态，不含通知正文、整页 HTML、
账号或凭据。回归测试重复采样是离线模拟，不冒充实时稳定采样。
本次没有生成正式价格快照，也没有操作预订。

## 可选官网表单实验入口

网页增加“查询入口”选择；API 增加 `entry_mode: "direct" | "form"`。
省略仍为 `direct`，旧任务显示为直达；CLI 保持原来的直达模式。
表单模式不修改正式 provider 注册状态，也不读取任何平台 API key。

`FormEntry` 使用官网已观察的可见控件执行：

1. 只导航首页一次，等待查询组件；选择单程，确认返回日期控件消失。
2. 依次输入机场代码，点击代码精确匹配的候选项；SHA 模糊结果中出现 PVG
   等候选时不能按第一项选择。选定后必须读到独立机场代码，不能只相信输入文字。
3. 通过只读日期框的真实日历选择日期，核对年份、月份、日期；最多 12 次翻月，
   仅支持今天至未来 365 天内。日历价格不采集；具体可选范围仍由官网决定。
4. 在乘客控件中将婴儿、儿童归零，再设为 1 成人。特殊乘客必须已经为零，
   否则停止，不擅自改变个人资格声明。
5. 提交前核对机场、日期、人数、单程、选择控件关闭及唯一查询按钮。
   持久化核对结果后再次检查；只点击一次“查询”。
6. 不对结果 URL 再执行 `goto`；沿用当前页交给已有通知、等待、解析流程。

浏览器控件操作不使用 force、JS 写输入值、内部状态、Cookie 复制或接口重放。
表单阶段受 `min(provider.timeout_ms, 60000)` 毫秒约束（示例配置 45 秒），
整个任务仍受 240 秒约束。提交前出现验证码/未知弹窗则停止本次任务；
已进入结果页后的验证仍可沿用现有人工继续机制，不重提表单。
结果页地址匹配只证明已导航，不证明报价成功；SPA 不把首页 HTTP 200
当作航班查询成功。超时、取消、失败、空结果均不会自动换入口或重试。

顶层 `entry_evidence` 独立保存：入口、阶段、固定原因代码、提交尝试标记、
结果页观察标记及条件核对布尔值。错误/取消/总超时保留记录；不包含原始
表单 HTML、账号、输入原文、会话凭据或网络响应。`submit_attempted=true`
表示可能已经提交，不能解释为官网确认受理，也不能据此自动重提。

离线测试分为纯逻辑/生命周期回归与真实 Chrome 的全请求拦截模拟。
`airchina_form_mock.html` 是合成控件，不是官网网页或真实可用性证据：
覆盖动态 placeholder、模糊候选、翻月、遗留多人设置归零、一次 SPA 提交、
错误日期/机场/特殊乘客拒绝。真实验收另行记录，不能把离线通过当成无人值守可用。

## 与携程查询方式逐项对照

| 项目 | 对齐方式 | 保留的区别 |
|---|---|---|
| 浏览器启动/后端 | 共用 BrowserSessionManager 与后端注册表 | 不因验证码切换后端重新搜索 |
| 请求头注入 | 共用 `provider.extra_headers → backend.new_context` | 不复制携程 Cookie、认证头、Host、Origin、Referer |
| 浏览器环境 | 两者示例均为 `zh-CN`、`Asia/Shanghai` | 由各自配置和浏览器产生实际站点请求 |
| 通用请求头 | 两者示例均仅手动设置 `Accept-Language: zh-CN,zh;q=0.9` | UA 等保持浏览器默认，不假造国航专属签名 |
| 会话 | 共用已保存会话/持久 profile 机制 | `ctrip_state.json` 与 `airchina_state.json` 隔离；跨次有效性待实测 |
| 节流/页面超时 | 两者示例均 4–8 秒节流、45 秒页面超时 | 实验任务另有含人工等待的 240 秒总时限 |
| 入口 | 显式入口与条件复核 | 国航提供直达/表单实验模式；失败不自动 fallback，不照抄携程选择器 |
| 等待 | 有界等待和稳定证据，不以固定 sleep 判定成功 | 国航比较校验后的报价/列表质量，每次重验上下文；携程还利用响应代次/异步批次 |
| 解析 | 行程条件与航班及价格绑定 | 国航目前只校准可见 DOM，不套用携程结构化响应字段 |
| 失败 | 限流/验证/过期/上下文变化均停止或请求人工处理 | 不复制携程 profile 轮换、页面补救及通用价格兜底 |
| 结果 | 明确来源、价格类型、覆盖范围 | 国航基础票价不冒充正式 `ProviderQueryOutcome.price` |

“尽可能复用”指复用机制与校验标准，不是把携程的站点身份、
接口路径、签名字段、页面 DOM 或金额口径原样搬到国航。
仍待进一步验证：表单跨航线与跨次可靠性、结构化响应解析、往返/联程、
税费总价、无结果的上游原因与跨次会话复用。没有声称这些已实现。

## 访问阻塞的独立记录

## 跨任务同页复用实验

目的仅是验证“频繁重建浏览器上下文是否影响验证码触发”，不是免验证方案。
原先每个后台任务调用独立 `asyncio.run`，不能直接把其 Playwright 对象保存给
下一任务。现在由懒启动的专用线程和同一事件循环拥有国航实验浏览器，
普通携程、飞猪、甩尾查询不切换到该线程。任务仍由共享 `run_lock` 串行准入。

- `fresh`：每任务重建浏览器/上下文，完成后关闭；可作为对照。
- `reuse`：只有本次成功取得经校验的参考票价或产品后，才保留同一
  `automation/context/page`。人工验证后成功读取也适用；验证码本身没有自动操作。
- 空闲 600 秒自动关闭；会话从建立起最多保留 1800 秒。活跃任务不被空闲
  回收打断，总寿命到期时在任务结束后关闭，不延长下一次保留期。
- 取消、总超时、异常、验证未通过、空结果、过期结果等均关闭，不保留可疑
  会话继续搜索。清理结果不确定时禁止再次创建会话，要求重启应用。
- 浏览器设置、provider 配置或档案偏好文件改变，或用户关闭了页面，
  下次显式任务先清理原对象再新建；不自动尝试第二次查询。
- 应用退出关闭保留的上下文及线程；应用重启不能恢复旧 page 对象。
  国航档案维护操作也必须先取得公共锁并关闭空闲实验浏览器，避免在线清理档案。

任务之间释放公共查询锁，但不对浏览器自动刷新或发起新任务。每次用户提交仍
按选定入口正常导航/填写，重新核对航线、日期与报价；同一 page 对象不意味着
跨导航保留页面 JS 内存。没有复制存储、提取验证 token、轮换 IP/profile、
自动识别验证码，也没有将旧价格缓存伪装成新报价。

`session_evidence` 保存模式、本次是否复用、固定原因、会话内任务次数、
结束时处置及本地随机分组 ID；分组 ID 不是站点 session/token。
不包含路径、请求头、Cookie、账号或页面内容。记录是历史快照，
空闲自动关闭后不会改写过去任务的“结束时保留”；界面明确不保证目前仍打开。
旧任务不会补造复用证据。重复任务保持现有互斥拒绝，没有新增自动合并或缓存返回。

验收分离：
1. 单元测试验证同一对象/循环复用、配置变化、超时/取消/异常、空闲及总寿命回收。
2. 全请求拦截的真实 Chrome 离线实验验证两次显式任务使用同一页面/上下文/循环，
   合成页面的测试状态跨导航保留；重启对照会重新创建上下文。
3. 国航线上是否减少验证码仍未验收；不能把离线生命周期测试当作成功率证据。
   后续对照应固定入口、航线、日期与其他设置，分别记录实际复用标记、
   验证出现次数和有效结果次数，避免混淆首次建会话与真正复用。

## 单次查询网络诊断

实验任务新增独立的 `network_diagnostics`，不改变正式报价或验证码处理逻辑。
在导航前挂接浏览器事件，按启动、首页、填写、核对、提交、结果读取等阶段
记录耗时、请求/响应计数、HTTP 状态、网络失败分类及页面脚本异常计数。
HTTP 403/429 等返回与 DNS、连接、TLS、超时等传输失败分别记录。

- 只被动观察本次页面自然发生的请求，不重放、不重试、不发额外探测请求。
- 不读取请求头、请求体、响应正文、Cookie、存储内容或脚本错误正文；
  不保存 URL、域名原文、路径或查询参数。域名仅归为官网主站、国航子域、外部。
- “疑似查询请求”只代表国航域内 XHR/fetch 的路径关键词命中；
  不能证明真正查价接口被调用。未知业务响应暂不解析，HTTP 200 不能证明出票、
  有票或验证成功；外部资源报错不能直接归因于查价接口。
- 最多跟踪 256 个未结束请求、保留最近 100 条事件和 40 个阶段；
  超限有显式截断计数。观察期间定时保存，结束时保存最终快照，
  取消/超时/异常也保留已有证据。诊断未完整挂接会明确标记。
- 每任务使用独立监听器与请求集合。任务结束拆除监听器，避免同页复用时重复统计；
  下一任务不接收上一任务已发出请求的迟到响应。关闭浏览器产生的请求取消
  不记作查价过程中网络失败。
- 页面单列浏览器后端、持久档案启用与保存状态加载情况；这些不是认证有效性证明，
  与 `session_evidence.reused`（同一 page/context 对象复用）互不替代。

任务终态在清理和最终审计完成后发布，避免页面停止轮询后仍显示“会话使用中”。
当前为诊断能力与离线回归验收；不宣称新增诊断已取得国航线上票价。

## 借鉴携程的手动访问状态保存

现有 `BrowserAutomation.bootstrap_session(..., manual=True)` 和
`BrowserProfileService.open_browser_profile` 都能用于国航，不需要另造“验证码缓存”。
原先仅对 enabled provider 展示的档案入口，现在允许已配置但正式查询未启用的
国航出现；这不会启用国航正式查询或甩尾比价。打开恢复档案时保存其确切名称，
避免 `recovery-2` 等被误当成主档案偏好。

三种机制要区分：

| 机制 | 项目行为 | 不代表什么 |
|---|---|---|
| Chrome 持久档案 | 手动打开与查询共用所选国航项目 `user_data_dir`；Chrome 自己持久化站点数据 | 不是应用内浏览器、个人 Chrome 或携程档案；不能保证站点验证状态持久有效 |
| Playwright 保存状态 | 手动 bootstrap 后按现有策略导出并在后续上下文加载 `storage_state` | 不是完整页面内存，也不等同 Chrome 持久档案；Chrome 后端不读取该 JSON |
| 实验短时复用 | 成功参考读取后保留同一 page/context，供后续显式任务使用 | 不缓存旧报价；首次创建上下文不等于清空持久档案 |

推荐手动初始化路径（需要用户实际操作，尚不能认定本轮已完成）：

1. 确认使用与实验相同的配置文件/runtime 目录和 Chrome 后端，先结束实验任务。
2. 在“浏览器档案”打开**国航所选档案**。入口会先关闭空闲实验浏览器。
3. 用户在该项目窗口手动访问官网；若有登录或验证码，由用户自行处理。
   不从其他窗口复制认证资料，不把应用内浏览器成功访问当成项目档案已准备好。
4. 正常关闭这个项目 Chrome 窗口，再发起实验；不让手动窗口和自动查询同时占用档案。
5. 核对新任务的档案来源与查询结果；若仍出现验证，继续按“遇阻处理”设置停止/等待，
   不自动换档案或循环重试。记录“档案已加载”和“查询成功”两个独立结论。

状态文件/档案属于敏感本地运行数据，不能上传或提交到 Git。
新增离线测试验证手动入口与后续查询选择同一档案、Chrome/Playwright 各自保存策略、
网络事件脱敏/有界性/跨任务隔离、失败审计持久化及界面展示。

#### 结论与下一项对照

当前能够确认：同文档、同 Page/context 的新查询仍可能要求验证；读取已验证
结果和发起新查价不是同一行为。不能确认“每查必验”，也不能把频控、自动化
环境或某个请求头定为根因。机场控件超时与重复验证应继续分开诊断。

优先补普通浏览器环境对照：由用户自行正常启动 Chrome，在相同网络、相同查询
条件下操作；记录首轮与一次同条件续查的提交时间、是否出现验证和结果。
如首轮出现验证，仅由用户完成；第二轮再遇验证则停止，不再连续尝试。
不复制个人档案、验证材料或更换网络。此对照只能比较整体环境（包括档案历史），
不能单独证明某个启动参数导致问题。若普通浏览器正常而项目环境持续异常，
再按单变量原则排查环境差异；若两者都出现，则应优先寻求官网解释或授权渠道，
而不是继续修改自动化点击。
