# 飞猪官方 CLI：甩尾查询与使用限制

## 安装与接入

验证日期：2026-10-27；验证版本：`@fly-ai/flyai-cli@1.0.16`。
本次使用经过 npm integrity 校验的独立发布包、独立配置目录验证，没有改动全局安装或使用个人密钥。
部署机器需安装 Node.js 18+，并确保运行本项目的进程能找到 `flyai`：

```sh
npm install -g @fly-ai/flyai-cli@1.0.16
flyai search-flight --help
```

飞猪官网直接链接 AI 开放平台及 `alibaba-flyai/flyai-skill` 官方仓库；仓库链接上述 npm 包。
如需正式 Key，请自行登录官方控制台获取并按其说明配置：

```sh
flyai config set FLYAI_API_KEY "your-key"
```

已通过 `config set --help` 确认 1.0.16 支持配置命令（主帮助没有列出该隐藏命令）。
配置写入执行用户的 `~/.flyai/config.json`；服务账户与交互式终端账户不同时注意配置位置。
不要将密钥提交到 Git、测试夹具或日志。正式 Key 的额度、费用、商用授权仍以控制台/官方确认为准，
本次未申请 Key、充值、付费或测试正式 Key。

## 在项目中使用

在“甩尾发现”选择飞猪，填写 A（出发）、B（实际目的城市/中转城市）、日期、舱位和候选 C 后启动。
现有 API 与界面参数不变：

- 组合搜索：A→C，加 `--journey-type 2 --transfer-city B`，城市代码转换为中文城市名。
- 直飞基准：A→B，加 `--journey-type 1`。
- 经济舱也显式传递 `--seat-class-name economy`。
- 商务舱/头等舱组合传 `business,first`。公开 CLI 未明确单列超级经济舱筛选，
  当前经济舱族查询不能保证超级经济舱覆盖，最终以返回的实际舱位校验为准。
- 上游返回后仍逐项检查实际两段路线、日期、舱位、航司和时段，不盲目信任搜索参数。
- CLI 不能证明完整覆盖；空结果/未返回目标中转显示 `search_incomplete`，可重试，不写无航线负缓存。
  飞猪旧版本的无航线负缓存也不再用于跳过查询。平台限流冷却仍然生效。
- 平台 `systemMessage`、体验模式和覆盖范围保存在报价元数据中，并通过结果 API 显示在待核实事项里。
- `status` 非成功的业务响应按错误处理，不将返回空数组的限流/鉴权失败当作无票。

单独验证示例（实际使用时更换未来日期）：

```sh
flyai search-flight --origin 北京 --destination 杭州 \
  --dep-date 2026-10-28 --journey-type 2 --transfer-city 郑州 \
  --seat-class-name economy --sort-type 3
```

没有进行批量压测、下单、支付或出票。项目端到端验证使用独立 SQLite 数据库。

### 关键限制

1. **体验模式结果受限**：响应明确提示部分搜索结果可能受限，建议获取正式 API Key。
   此次两类查询均返回两条，但不能据此断言硬上限就是两条。未发现可确认的分页/全量拉取参数。
2. **价格范围未确认**：两条中转的 `ticketPrice` 与对应首段直飞的字段值相同；此前网页相同行程显示了不同金额。
   这不能证明该字段必然是首段价，也不能证明一定是两段总价或缓存错误。
   项目因此标记 `price_scope=unknown`，显示“平台 ticketPrice · 整段总价未核实”。
3. **税费、库存、人数未知**：这次返回未给出可证明的税费包含状态、计价人数或多人可售库存；
   `quantity` 为 null。`--help` 未提供人数参数，不自行编造。
   当前不会根据这些结果显示确定的节省金额。
4. **城市级查询**：城市/机场代码转换为城市名可能覆盖同城多个机场；仍需用返回航段校验实际机场。
5. **覆盖率与频控**：没有测试配额上限，也不承诺不限频、无风控或固定响应速度；
   保持串行、查询预算和冷却，429 停止，不通过更换身份/后端绕过。
6. **购票能力**：当前公开命令用于搜索，结果含预订跳转链接；没有在本项目接入自动下单、支付或出票。
7. **公开包的环境信息**：发布包 README 描述了设备随机标识及基本环境信息的发送，用于签名和风控。
   本次只运行正常 CLI，没有提取内置凭证或重写其请求签名。

## 2026-10-27 后续验证：可选目的地与定向基准

使用用户授权的正式 Key 做两次额外只读查询，结束后已清理临时密钥。

### 不填最终目的地：可用，但非全量

```sh
flyai search-flight --origin 北京 --dep-date 2026-10-28 \
  --journey-type 2 --transfer-city 郑州 --seat-class-name economy --sort-type 3
```

返回 status=0、9 条结果，末段目的地分别为 DAT、DLC、TAO、DOY、AQG、WUA、BZX、TEN、TCG。
没有体验模式提示。此前指定 HGH 时能查到结果，这次未包含 HGH；
两次查询非同时进行，但至少不能将开放目的地搜索视为完整枚举。
部分返回的航班标识/舱位也需要逐航段检查，不应把所有返回记录都当作已经可出票的方案。

适配器支持 `destination=None`（命令中省略 --destination）。
**UI 现已接入开放目的地模式**：选择飞猪 → 重新探索 → 目的地查询方式「开放目的地发现」。
默认仍为逐候选城市查询，只有显式选择开放模式才不限制最终目的地。
开放模式的完整用法和恢复语义见下节。

### 指定首段航班：可用，已接入补充基准

```sh
flyai search-flight --origin 北京 --destination 郑州 --dep-date 2026-10-28 \
  --journey-type 1 --transport-no CA1915 --seat-class-name economy --sort-type 3
```

成功返回 CA1915 一条，ticketPrice=380；这是本次字段值，不是承诺价格，
也不与较早时刻的报价混算节省。

当初始直飞查询没有覆盖已发现的某个首段时，执行器使用 `transport_no` 补查：

- 筛选去重后按 `max_baseline_queries` 的本轮总预算补查（默认 3 次）；同次运行的相同首段不重复补查。
- 已有同航班基准不额外查询；额外请求前等待，受任务总时间预算及取消控制。
- 按航班号、时间、机场、日期、实际舱位组成的首段标识再次核验，不信任上游筛选。
- 定向结果只补充同航班基准，不冒充全市场最低价；未核实口径仍不计算确定节省。
- 若补查触发限流，保留已采集报价，停止后续查询并进入平台冷却。

### 文档与实测字段兼容

官方 `skills/flyai/references/search-flight.md` 示例给出 `adultPrice: "¥400.0"`、
`duration: "140分钟"`；实际响应常为 `ticketPrice: "563.00"`、`duration: "110"`。

现支持两种格式；ticketPrice 非空时优先，缺失时回退 adultPrice，保留字段名称和原值。
只接受完整的正数格式，可含 CNY/RMB/人民币符号和规范千分位；
范围价、“起”价、负数、NaN、Infinity、其他货币等不强行提取数字。
字段名 adultPrice 不自动证明人数计价、税费或整段价格范围。

## 开放目的地模式：界面、API 与恢复语义

1. 选择「飞猪」平台、「重新探索」查询模式，目的地查询方式选「开放目的地发现（非全量）」。
2. 输入出发 A、中转 B、日期、舱位；价格、出发时段、航司仍作为返回后的校验条件。
3. 最终目的地候选列表隐藏且不传给 CLI。平台返回哪些实际城市，就逐条校验、保存哪些城市。
4. 结果按实际目的地及首段存储、分组；每个实际目的地各自保留尾段备选，不把同首段的多个城市截成三个。

```json
{
  "provider": "feizhu",
  "search_scope": "open",
  "mode": "explore",
  "origin": "BJS",
  "transfer": "CGO",
  "departure_date": "2027-06-20",
  "cabin": "economy",
  "candidates": [],
  "max_candidates": 0,
  "target_results": 0,
  "max_minutes": 2
}
```

使用现有 `POST /api/tail-discovery/run`，不需要新端点。`search_scope` 默认 `candidates`，
其他平台不接受 `open`。开放查询不支持城市数预算和首段目标预算（界面禁用，API 非零拒绝）；
因为一次返回的城市数量不可预测，不能把城市预算误解释为供应商调用次数。
总运行时间预算和取消保持有效。一次任务通常为一次直飞基准、一次开放查询，
按 `max_baseline_queries` 再补查缺失的同航班基准（默认最多 3 次，0 关闭），串行运行，不进行隐式分页。
该预算按本轮任务累计而非每个城市分别计算；只补查已通过本地筛选及去重后保留的首段，相同首段跨城市复用。
默认 `filter_scope=first_leg` 仅约束实际乘坐的首段舱位与航司，CLI 不传整程舱位限制；
`filter_scope=all_legs` 要求全行程每一段都符合。路线、时间及日期仍始终校验两段。
复核会把原首段航班号传给中转搜索，但不假定平台一定严格或完整返回；
未匹配完整原行程时标为“无法确认”，可以继续重试，不作为下架证据。

### 检查点与恢复

- 任务进度单位为一个「开放查询批次」，不是所有可能目的地。
- 内部检查点使用 `__OPEN__` 标识这一批次；**报价记录和航线连接仍使用真实目的地**。
- 一次响应的有效报价、尝试记录和检查点在同一事务中提交。
  事务失败整体回滚；未完成/失败批次可继续重试。
- 已提交成功的批次在“继续未完成项”时直接恢复结果，不发第二次开放查询，也不假装翻页。
  想重新访问平台请选择“重新探索”。
- 空响应或未返回可用路线是 `search_incomplete`，可重试，不证明没有航线。
  若响应有行程但均被用户条件过滤，则完成当前批次；修改筛选后应重新探索。
- 从开放任务点击“刷新已发现报价”，转为对数据库已发现城市进行定向查询。
  单条复核同样只查该条的实际目的地和具体行程。
- 飞猪旧的无航线负缓存不参与开放或定向搜索；平台限流冷却仍有效。

本次界面/任务接入使用此前真实响应的脱敏夹具、独立数据库和离线浏览器验证；
没有再次使用 Key 或消耗真实查询额度。部署运行仍需在服务进程使用的账户中配置自己的 CLI 和 Key。

## 历史引导混合发现

新增显式 `search_scope=hybrid`，先开放取样，再根据历史及本次结果定向补查；
原 `open` 不会自动变成多城市扫描。默认补查上限 5 城市、总调用尝试上限 20 次，
总调用包含初始基准、开放、定向及同航班补查，错误尝试也计数。
可在界面查看每个待查城市的优先理由。恢复成功开放批次不重复请求。
详细语义及离线回放见 [历史引导发现](HISTORY_GUIDED_DISCOVERY.md)。
