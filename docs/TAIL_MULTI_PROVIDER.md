# 携程 + 飞猪联合甩尾查询

## 使用方式

1. 查询平台选择 **携程 + 飞猪同时查**，填写出发地、想抵达城市、日期和共同筛选条件。
2. 点击一次「开始搜索」创建一个联合任务，两平台并行执行。
3. 页面分别显示平台进度、保存报价数和失败原因。结果在同一列表展示，可展开「筛选」
   选择报价平台；平台过滤仍只作用于已加载结果。

没有本地偏好时，平台默认选双平台；已保存的单平台偏好继续保留，不强行改动。
依然可以选择仅携程或仅飞猪。此功能不新增依赖、不修改或上传本地凭据。
飞猪需要现有官方 CLI、凭据及平台启用配置；未启用、CLI 不可用、授权失败或冷却
只影响飞猪子任务，携程仍可运行。此轮只进行离线验证，不保证平台当前线上可用。

## 检索方式和预算

共同条件包括出发地、抵达城市、日期、人数、舱位、航司、时间范围、查询价格上限及
首段 / 全程筛选范围。不同平台仍遵循各自已有的校验及报价限制。

| 设置 | 携程 | 飞猪 |
| --- | --- | --- |
| 默认检索 | 已选尾段城市 | 开放目的地发现，非全量 |
| 可选方式 | 候选城市 | 同候选城市 / 开放发现 / 开放 + 历史引导补查 |
| 城市数、首段停止目标 | 使用表单预算 | 定向模式使用；开放 / 混合模式不用 |
| 时间上限 | 本平台独立计时 | 本平台独立计时 |
| 本轮调用上限、同首段基准补查 | 不适用 | 使用表单预算 |
| 定向补查城市上限 | 不适用 | 混合模式使用 |

**预算不是两个平台共享的总额。** 例如定向模式城市上限 3，表示每个平台各查最多
3 个候选城市，不是两平台合计 3 个。调用预算仅统计飞猪调用尝试，不等同计费次数。
开放发现不是完整库存；携程与飞猪不保证发现相同的尾段城市。

## 执行与恢复

- 父任务持有原应用全局查询锁，外部其他查询仍不能同时启动。父任务内部使用
  `asyncio` 并行运行两个独立 `TailDiscoveryService`，每个子任务有独立的锁、
  检查点、预算、限流冷却与诊断 JSON。没有用户可传入的“绕过全局锁”参数。
- 子任务写入同一 SQLite 库。历史任务列表只显示父任务，平台子任务状态从父任务的
  `progress.children` / `result.children` 查看，不提供 UI 独立停止子任务的入口。
- 一个平台异常不取消另一平台；已完成结果即时可读。部分失败或暂停时父任务显示
  `partial`，两者都失败显示 `failed`，不会把部分失败包装为成功。
- 携程等待人工验证时，飞猪继续运行；「继续验证」只发送给携程。
- 「停止查询」向两个子任务发出协作停止信号，等待它们退出后才释放全局锁。
- 「继续未完成平台」复用完成平台的结果，只继续其他平台。失败后已保存的城市检查点
  也会复用，不反复查已经完成的城市。「重试失败平台」只重试失败子任务。
- 「重新查询两个平台」是新探索，两个平台都重新运行；「重新查价」仅查询已发现目的地，
  某平台没有已发现目的地时单独报告，不阻断另一平台。
- 单条「复核报价」仍只查询报价所属平台，不自动查两个平台。
- 服务重启后父任务显示中断；继续时从持久化子任务和检查点恢复。秒级时间戳相同的
  连续提交也会优先恢复最新的活动父任务，避免错误解锁后重复发起。

## 报价归属与比较

联合结果按两个子任务的根检查点 ID 做 SQL 并集，再排序和分页，不按路线或最近
N 条历史报价猜测归属。没有子任务检查点的父任务返回空列表，不回退到全量历史。
继续任务保留复用平台和恢复平台的根检查点，原始历史任务仍可单独查看。

两个平台的同一首段不会被去重为一条报价，也不会放进一个跨平台的“最低价”分组。
平台、计价单位、人数、税费和有效期信息分别保留；价差仅使用各报价自己的可比基准，
不据此直接断言某平台更便宜或可出票。

## API

仍使用 `POST /api/tail-discovery/run`，新增：

```json
{
  "provider": "both",
  "origin": "BJS",
  "transfer": "SHA",
  "departure_date": "2027-06-20",
  "cabin": "economy",
  "candidates": ["CAN", "SZX"],
  "search_scope": "candidates",
  "feizhu_search_scope": "open",
  "max_candidates": 3,
  "max_minutes": 10,
  "max_provider_calls": 20
}
```

返回父任务的 `job_id`，继续使用现有 jobs / results / restart / cancel / continue /
retry-failed 接口。`provider=ctrip` 和 `provider=feizhu` 的单平台语义保持不变。
父任务和子任务的引用由服务端生成；客户端传入的内部 `_` 字段不被信任。

## 回归覆盖与限制

- `tests/test_tail_batch.py` 使用真实任务管理、校验和 SQLite 检查点，模拟平台传输：
  并行进入、全局锁、失败隔离、只重试失败平台、保存后崩溃恢复、人工验证、取消、
  平台禁用 / 冷却、全部失败、目的地模式、并集分页、服务重启、同秒提交、
  刷新空平台、内部参数注入和 HTTP API。
- `tests/test_tail_ui.cjs` 覆盖双平台独立设置、单请求 payload、平台筛选、避免跨平台去重 /
  最低价合并，以及失败恢复按钮和错误文本转义。
- `tests/browser_tail_smoke.py` 拦截所有页面请求，在本地模拟双平台部分失败，检查
  1280、390、320px 布局、单次 POST、独立进度和平台过滤；截图为模拟数据。
- 执行器仍是单进程后台任务，不是分布式任务队列。不同联合任务仍串行；
  本次不改变平台频率限制、不绕过人工验证、不承诺真实库存或出票能力。
