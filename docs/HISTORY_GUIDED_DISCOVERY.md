# 历史引导发现

## 三层证据，而不是库存地图

1. **航段连接**：有效行程中的 A→B、B→C，来源平台、航司、首次/最近观察时间。
2. **联程证据**：完整实际航段、出行日、查询上下文、结构校验质量。
3. **候选表现**：是否符合用户条件且校验通过、耗时、已确认的可比节省。

这是已观察路线图，不是全量时刻表。B→C 存在不代表 A→B→C 当前可售，更不代表出票。
本轮没有地图可视化面板，界面展示查询优先级和决策依据。

结构校验不使用价格、航司或舱位条件；超预算路线仍会积累。
缺时间等证据的路线只记录 `needs_review`，不提升为确认连接。
缺舱位而待复核的报价保持未知，不当成“用户条件不匹配”。
报价、证据、城市表现与检查点共用事务，失败一起回滚。
同一原任务、源查询、行程具有唯一键；恢复已完成项不增加票数。
重试失败查询更新记录，未再次返回的正向证据不自动变成负面。
旧数据保留，只把近期旧命中作为有上限的弱提示，不批量伪造新证据。

## 排序规则

`tail_history.rank_candidates` 是确定性的纯函数，输出城市、规则评分、估计耗时和原因。
评分不是校准后的成功概率，也不是省钱承诺。

- 相似度参考平台、舱位、人数、首段/全程范围、航司、出发时段、价格上限、出行日期、星期及提前预订天数。
- 历史按 7 天半衰期衰减；超过 90 天或晚于评分时点的证据不参与。
- 同一次查询同一城市的多个票价产品最多贡献一次路线正向权重。
- 开放响应按真实 C 记录命中，遗漏城市保持未知；批次耗时不作为单城市定向成本。
- “有路线但条件不合”影响报价实用性，不撤销路线存在证据。
- 其他平台只提供弱正向提示，不产生负向排除。
- 节省未知采用中性权重；成本未知使用飞猪 10 秒／携程 90 秒的**规则先验**，不是实测性能承诺。
- 每五个查询位置中的第二位优先探索；每批提交后重排尚未派发的城市。
- 界面展开“历史优先级与调用预算”查看理由，任务结果保存 `priority_trace`。

单次评分最多读取最近 6000 条联程证据、6000 条城市表现，以及有限的旧尝试和图连接，
这是有界历史样本，不是全库统计估计。

## 三种查询范围

- `candidates`：只重排所选城市，不扩大范围。
- `open`：飞猪一次开放取样，成功恢复不重复请求。
- `hybrid`：飞猪一个开放批次，然后定向补查。

混合候选池来自所选种子、近 60 天历史线索、本次结构有效的开放结果。
最多 500 个真实城市，另有一个内部 `__OPEN__` 查询单元；所选种子优先保留。
图里没有的城市不会被自动排除，池子也不代表平台全量。

```json
{
  "provider": "feizhu",
  "mode": "explore",
  "search_scope": "hybrid",
  "origin": "BJS",
  "transfer": "SHA",
  "departure_date": "2027-06-20",
  "cabin": "economy",
  "filter_scope": "first_leg",
  "candidates": ["CAN", "SZX"],
  "max_followup_candidates": 5,
  "max_provider_calls": 20,
  "max_baseline_queries": 3,
  "max_candidates": 0,
  "target_results": 0,
  "max_minutes": 5
}
```

网页选择“历史引导：开放发现＋定向补查（仅飞猪）”；混合模式中的候选列表是种子，可为空。

## 预算与恢复

- `max_followup_candidates` 默认 5，范围 0–50，按原任务累计已完成城市计算。
  当前轮失败尝试也占本轮城市配额；恢复时可重试失败项。达到上限后继续不会无限追加；
  希望增加探索应重新探索。
- `max_provider_calls` 包含初始基准、开放/定向和补基准，错误尝试也计数。
  每轮重置，不是平台扣费计数。UI 飞猪默认 20，混合 API 默认 20；0 明确表示不限。
  只有一次预算时省略初始基准，优先做发现；已耗尽不发下一次请求。
- 补基准另受 `max_baseline_queries` 限制，总预算优先于分项预算。
- `max_candidates`、`target_results` 在开放/混合模式中必须为 0，使用专门补查上限。
- 时间、取消、限流仍有效；调用预算耗尽不伪造平台冷却。
- 成功开放批次恢复时不重做；动态候选池不替换原种子或原查询指纹。
- 刷新混合任务转为已保存报价城市的定向刷新；“重试失败”复用检查点继续未完成项。
- 一批没有完成检查点时停止为 `runner_incomplete`，避免无限循环。
- 携程也使用历史和动态排序，但不支持混合开放模式或精确平台调用计数。

## 指标与回放

实际任务保存调用分类、本轮不同有效行程数／100 次飞猪调用尝试（含基准），
同一行程在开放和定向重复出现不重复计数。携程不生成没有调用计数依据的比率。

```sh
python tools/replay_tail_history.py cases.json --budget 3
```

案例格式：

```json
[
  {
    "observed_at": "2026-10-27T12:00:00+00:00",
    "request": {
      "provider": "feizhu", "origin": "BJS", "transfer": "SHA",
      "departure_date": "2027-06-20", "cabin": "economy"
    },
    "candidates": ["CAN", "SZX"],
    "gold": {
      "CAN": {"outcome": "matched", "elapsed_seconds": 12},
      "SZX": {"outcome": "filtered", "elapsed_seconds": 10}
    }
  }
]
```

固定顺序与历史排序共用严格早于本案例的历史；本案例及同时间案例答案不可用于排序。
缺少某候选标签时跳过该案例的策略比较，**不把缺失的反事实当成失败**。
回放按每候选一次搜索计数，不含基准或补查，与线上总调用指标口径不同。
合成测试只验证逻辑，不证明线上效率已经提升；真实收益仍需足够完整的历史样本或受控比较。
