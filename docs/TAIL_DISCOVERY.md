# 甩尾发现：查询、报价与任务恢复

## 查询模型

输入 A、目标城市 B、出发日与候选 C，查询 A→B→C 两航段组合。
平台返回多条候选，而不是提前只选最低价。服务层按以下顺序处理：

1. 价格上限、出发时段过滤；
2. 航段、日期、航司、实际舱位校验；
3. 具体行程去重，并按首段航班保留若干尾段方案；
4. 附加报价口径、两类基准、采集时间和有效期；
5. 在一个 SQLite 事务内保存结果、尝试记录和目的地检查点。

缺少舱位或日期证据的结果进入“待复核”，不算作已校验首段。
没有可信证据的价格、结构不完整的接口响应不作为成功报价或无航线负缓存。
UI 按实际到达 B 的首段航班分组，再展示不同 C；不同币种、人数、计价单位不混成同一组。

## 四种执行模式

| mode | 行为 |
| --- | --- |
| `explore` | 新任务，查询候选集；不继承之前任务的完成状态，携程可使用负缓存；飞猪 CLI 不保证覆盖，不使用无航线负缓存 |
| `resume` | 指定 `source_job_id`，继续原任务未完成/失败项；不重查已完成项 |
| `refresh` | 重查当前条件下已发现报价的目的地，不跳过成功项，也不使用负缓存 |
| `recheck` | 通过结果 ID 发起，重查指定的具体行程，不自动替换成其他航班 |

继续任务保留原查询条件（含人数、时段等），预算按本次执行重新计算。
候选顺序变化不改变查询指纹；改变查询条件应选择“重新探索”。
中断后浏览器需要重新打开，但已提交的 SQLite 检查点不会丢失。
旧版本 JSON 队列只保留为诊断文件，不再决定跳过哪些目的地；旧任务没有新检查点时会重查。

“重载已保存结果”仅更新页面；“刷新已发现报价”才会访问平台。
飞猪额外支持 `search_scope=open`：省略最终目的地，一次发现多个尾段城市，但不是全量。
该选项独立于 explore/resume 执行模式；一个响应作为一个事务检查点。
继续成功批次不会再次查询；刷新已发现报价和单条复核转为实际目的地定向查询。
开放模式仅支持运行时间预算，城市数和首段目标预算必须为 0；详见 `FEIZHU_CLI.md`。
单条复核允许价格上涨，不受原先价格上限阻止；旧记录保留，复核失败/未找到时旧价失效。
任何搜索结果都不表示预订、出票或库存已锁定。

## 报价比较

`raw_payload.quote_terms` 显式记录：

- `currency`
- `price_basis`：`per_person` / `party_total` / `unknown`
- `tax_included`：true / false / null
- `requested_passengers`、`priced_passengers`、`inventory_verified`
- `fare_conditions`、行李和票规的未知状态

`raw_payload.baselines` 同时提供：

- `market`：满足出发时段、航司、实际舱位条件的 A→B 最低直飞价；
- `same_flight`：与组合首段航班匹配的单买价。

只有币种、计价单位、税费与人数口径一致，且采集时间相差不超过 20 分钟时才计算可比节省金额。
同航班比较还要求票价条件一致。否则返回 `reference_only` 和具体原因，不输出误导性的节省金额。
无法找到匹配航班/舱位证据时，基准为 `unavailable`，不会借用低价日历充当精确基准。

**当前接入限制：**飞猪 CLI 没有在本项目中验证多人参数/多人库存，浏览器采集也不能证明库存锁定。
两种接入默认将未确认的计价单位、税费、票规保持为 unknown/null。
飞猪 CLI 定向搜索会传中转城市与中转类型，基准明确查直飞；体验模式提示保留在结果中。
实测 `ticketPrice` 的整段计价范围仍无法确认，详见 [飞猪 CLI 验证及限制](FEIZHU_CLI.md)。
因此真实数据中“仅供参考／暂无可比基准”是正常保守行为，不应为了显示节省数字填造字段。
未来适配器只有在获得明确数据后才应填写可比较的口径。

报价默认 20 分钟过期，可用 `quote_ttl_minutes` 设置 1–120 分钟。
这只是本地展示时效，不是平台保价承诺。
`observed_at` 不会因重新读取数据库而更新。旧版本缺少有效期的记录显示为历史报价。

## 查询预算与候选排序

请求可设置：

- `max_candidates`：本次最多查询目的地数，0 表示不限；
- `max_minutes`：含基准查询和冷却的运行时限，0 表示不限；
- `target_results`：找到指定数量的不同已校验首段后停止，0 表示不限；
- `alternatives_per_flight`：每个目的地、每个首段保留的最大方案数，默认 3；
- `ignore_cache`：绕过 6 小时无结果缓存，不绕过平台限流冷却。

排序为确定性的规则评分：时间衰减的有效命中率 × 预期可比节省 ÷ 查询成本。
没有历史时使用明确的先验，历史半衰期为 7 天；约每 5 个位置保留一个新候选探索位。
浏览器超时/验证失败不作为“没有航线”的负样本，其他平台只提供弱正向排序提示，不做排除。

每个目的地无论成功或无结果都会发布进度并执行冷却。
429/限流会停止当前扫描，并保存 10 分钟平台冷却；不通过切换后端绕过限流。
验证统一进入人工等待，完成后点“继续验证”；超时后可恢复未完成项。
CLI 超时或任务取消会终止本次启动的进程树，避免释放运行锁后遗留查询进程。

## 存储与迁移

初始化数据库时增量创建：

- `tail_candidate_checkpoints`：以原始任务 ID + 目的地为键，保存查询指纹、状态、尝试与结果 ID；
- `tail_provider_cooldowns`：平台级限流冷却；
- `tail_discovery_results.itinerary_key`：同一时刻不同航班不再互相覆盖。

没有删除历史数据。上线前仍建议备份数据库。
事务内使用线程本地连接，让结果、尝试、航线连接和检查点一起提交或回滚。
任务仍为本地单实例架构；没有改成分布式队列或多 worker 协调。

## API

```text
POST /api/tail-discovery/run
POST /api/tail-discovery/jobs/{job_id}/restart   {"mode": "resume" | "refresh" | "explore"}
POST /api/tail-discovery/results/{result_id}/recheck
POST /api/tail-discovery/jobs/{job_id}/continue
POST /api/tail-discovery/jobs/{job_id}/retry-failed
```

无效参数返回 400、缺失任务/报价返回 404、运行冲突或限流冷却返回 409。
任务运行中的人工验证继续与已结束任务的断点继续是两个不同动作。

## 验证

使用 Python 3.10+（可选 browser-use 需要 3.11+）。

```sh
python -m pip install -r requirements-dev.txt
python -m pytest -q
node --test tests/test_tail_ui.cjs
python tests/browser_tail_smoke.py --output-dir ./runtime/tail-ui-smoke
```

浏览器烟雾测试使用系统 Chrome 和隔离临时 profile，拦截全部 HTTP 请求，
只通过本地 TestClient 返回模拟页面/数据，不访问航班平台。
它检查桌面、390px、320px 页面及“重新查询此行程／继续任务”操作。
自动测试不能代替真实平台页面变化、真实票价口径以及 Windows 环境的人工验收。
